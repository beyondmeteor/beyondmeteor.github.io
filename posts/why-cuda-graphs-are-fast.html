Why CUDA Graphs Accelerate LLM Inference

The main gain is reduced repeated CPU/driver launch overhead, not magically faster GPU arithmetic.

1. The problem: many short launches

During decode, each generated token may require many kernels: normalization, matrix operations, attention, and sampling. If individual kernels are short, host-side launch overhead and gaps between kernels become significant.

→
GPU K1
→
CPU launch K2
→
GPU K2

A CUDA Graph records a GPU work DAG with dependencies. Instantiation prepares an executable graph. Subsequent cudaGraphLaunch calls submit that graph more efficiently than many individual host launches. GPU scheduling still exists; the work is not simply precomputed.

3. Minimal PyTorch experiment

import torch
x = torch.randn(4096, device="cuda")
static_x = torch.empty_like(x)
for _ in range(5):
    y = torch.relu(static_x * 1.1 + 0.3)
torch.cuda.synchronize()
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    y = torch.relu(static_x * 1.1 + 0.3)
static_x.copy_(x)
g.replay()
torch.cuda.synchronize()
print(y[:4])

The graph uses stable tensor addresses. Compare many repeated eager executions with replays using CUDA events, plus Nsight Systems to identify CPU launch gaps. Synchronize appropriately when collecting timings.

4. When does it help?

WorkloadExpected impact
Decode, many small kernelsOften substantial host-overhead reduction
Long, compute-heavy prefillMay be less launch-bound
Changing shapes / addressesMay require multiple captured graphs, padding, or eager fallback
Dynamic allocations / unsupported capture opsCapture can fail or require refactoring
Measure end-to-end tokens/s and token latency, not just the time of a single kernel. CUDA Graphs can consume extra memory; exact benefits depend on model, batch shape, hardware, and framework.

5. Who schedules the graph?

Application/CPU submits the executable graph via the CUDA runtime/driver, and the GPU executes graph nodes respecting dependencies. This is execution-graph replay, not ahead-of-time model compilation.

CUDA Graph 为什么能够加速 LLM 推理？

核心收益主要是减少重复的 CPU/Driver Kernel 启动开销，而不是让 GPU 的数学运算凭空变快。

1. 问题：大量短 Kernel

Decode 每生成一个 Token，需要依次执行 Norm、矩阵运算、Attention、Sampling 等多个 Kernel。当单个 Kernel 很短时，CPU 发射指令以及 Kernel 之间的空闲间隔可能占据明显比例。

2. 捕获一次，重复回放

CUDA Graph 记录带依赖关系的 GPU 工作 DAG。实例化后得到可执行 Graph，CPU 后续通过 cudaGraphLaunch 更高效地提交整张图，减少逐个 Kernel 的 Host 启动工作。GPU 仍然需要真正执行计算和调度，而不是提前算好结果。

3. 最小 PyTorch 实验

import torch
x = torch.randn(4096, device="cuda")
static_x = torch.empty_like(x)
for _ in range(5):
    y = torch.relu(static_x * 1.1 + 0.3)
torch.cuda.synchronize()
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    y = torch.relu(static_x * 1.1 + 0.3)
static_x.copy_(x)
g.replay()
torch.cuda.synchronize()
print(y[:4])

Graph 使用固定的 Tensor 地址。实验应对比多轮普通 Eager 执行和 Graph Replay，通过 CUDA Events 测时，再结合 Nsight Systems 看 CPU Launch 间隙；测量时注意同步。

4. 哪些场景更有效？

场景预期效果
Decode：大量短 Kernel通常更容易减少启动开销
Prefill：长时间计算密集 Kernel启动开销占比可能较低
Shape / 地址频繁变化可能需要多套 Graph、Padding 或 Eager 回退
动态分配与不可捕获操作需要修改实现，甚至导致捕获失败
评估时重点看 Token 延迟和端到端吞吐，不能只看单个 Kernel 的运行时间。Graph 可能增加显存占用；收益受模型、Batch Shape、硬件和框架影响。

5. 谁调度 Graph？

应用侧 CPU 通过 CUDA Runtime/Driver 提交 Graph，GPU 按 DAG 依赖执行各节点。这是执行图的重放机制，并不等于提前编译完整 LLM。
